Navigation

Object navigation

Object navigation chooses what kind of object the user is working with. The global object model has five authoring types, in rail order: Text, Images bitmap, Shapes ready-made or parameterized vectors, Draw freeform vector edits, and Templates ready-made designs that may or may not be parameterized.

Use whenThe user needs to switch between object authoring modes.
Also in barMy Designs stays at the top and Ask is pinned to the bottom of the bar, separated by divider lines because they are global affordances, not object types.
MUIButtonBase items in a rail, with Tooltip on collapsed or icon-only variants.
Interactive example

Images

Image

Written context

  • Use the object rail to switch the command panel to the active object type.
  • Keep My Designs at the top and Ask pinned to the bottom of the rail as global affordances separated by divider lines.
  • Show Layout in this navigation only when one or more canvas objects are selected (the demo shows it because a sample object is on the bed).

Usage

  • Object navigation is the top level of the workspace. It holds the five authoring object types — Text, Images, Shapes, Draw, Templates — plus the global My Designs and Ask entries, and Layout while objects are selected. Every workspace command lives inside one of these.
  • Agents should not add, remove, or reorder navigation items. A new command belongs inside the panel of the object type it operates on — never as a new rail entry.
  • Clicking a navigation item opens that object type's command panel; clicking the active item again closes it.
  • Layout appears in the rail only while one or more canvas objects are selected; it disappears (and its panel closes) when the selection empties.
  • If a command does not clearly belong to one object type or to selected-object Layout, flag it for the user instead of guessing a home for it.

Selected image actions

Image

Written context

  • The image panel example uses the implemented full-width Create action and selected-image command grid.
  • The same selector changes the visual example and the written desktop/mobile guidance below.
  • Do not place broad option browsing in a cramped panel; promote it to a hero operation UI.

Usage

  • Use for object-specific commands only.
  • Show creation/import at the top of the active object panel.
  • Show selected-object actions only when the active or selected object matches that panel type.
  • Keep immediate or compact commands in the panel.
  • Open hero operation UI for extensive tweaking, async work, large option sets, preview-heavy choices, or See All browsing.

When the panel shows and hides

  • Initial state: on desktop the workspace opens with the Shapes panel already open; on mobile it opens with the panel closed and only the bottom dock visible.
  • Opening: the panel opens when the user clicks a rail or dock item, when they choose Edit on the selection pill or context menu (which opens the matching object-type panel directly in that object's edit tools), or when they choose Layout from the pill or menu.
  • Selection never toggles the panel. Selecting an object, switching the selection to a different object, or clicking empty canvas to deselect all leave the currently open panel exactly as it is. Panel content may adapt to the selection (for example, selected-image actions appear), but the panel itself does not open, close, or switch type.
  • Opening a panel with a matching selection: clicking a rail item while an object of that type is selected opens the panel directly in that object's edit tools.
  • Closing: the panel closes only via its close button, by clicking the active rail item a second time, or when a global overlay such as My Designs opens. Exception: the Layout panel also closes automatically when the selection becomes empty.

Focused surfaces

Hero operation UI

Hero operation UI is for object work that needs enough room to make decisions: a large preview, a large option set, multi-step generation, compare/review states, or extensive tuning. It follows the implemented `ImageCommandOverlay`: controls are a left sheet on desktop, preview is the large right-side stage, and mobile turns the controls into a draggable bottom sheet over the preview.

Use whenThe command cannot be comfortably completed as a single panel action because the user must browse, compare, preview, tune, generate, or review before committing.
MUIDialog or Drawer with Paper, AppBar, Slider, Tabs, Button, LinearProgress.
Interactive example

Create

Describe your image

Written context

  • Use the hero surface when an object command needs room for inputs, tabs, preview, generation, or review.
  • Use internal tabs when one operation contains meaningfully different command sets under the same goal.
  • The desktop/mobile selector changes both the example layout and the implementation guidance below.

Usage

  • The test: a command earns hero UI when the user has to see and judge a result before committing. If the result needs a big preview, a set of options to compare, or a wait, it is a hero operation. If the result lands on the canvas instantly and needs no review, it is a panel command.
  • Big preview to judge: Tune shows the filter applied to the whole photo before the user accepts it; Dithering needs the dot pattern shown at size; Remove background needs the user to check the mask against the subject.
  • Many options to compare: Create shows a grid of style cards (Linocut, Watercolor, Kawaii...) next to the prompt — the user compares before generating. A cramped panel cannot host that comparison.
  • Waiting on generation: "Make Magic!" runs async image generation; the hero preview is where progress and the finished result appear for review.
  • Stays in the panel: one-tap commands with immediate, obvious results — Add text, inserting a Circle, Smart Fit. No preview, no options, no wait: no hero UI.
  • Internal tabs are for peer paths to the same goal: Create has "New" (generate from a prompt) and "Recent Designs" (reuse an earlier result) — two ways to get an image. Do not use tabs to bundle unrelated commands into one hero surface.

Hero mode behavior

  • Object navigation is hidden while hero UI is open. On mobile the bottom dock is removed (ImagePanel focus mode → hideMobileDock); on desktop the full-viewport overlay covers the rail. The user finishes or exits the operation before switching object types.
  • The X button always exits. Every hero surface has a close button in its controls header that exits without applying; Escape and, on desktop, clicking the scrim do the same.

Mobile chrome

Bottom sheet

The bottom sheet is the single mobile-only container for workspace controls. The object command panel and the hero operation controls both become bottom sheets on mobile — same grip, same drag physics, same release rules. It overlays the canvas or preview rather than reflowing it, and it is never used on desktop.

SourceLeftPanel.tsx (command panel sheet) and ImageCommandOverlay.tsx (hero sheet).
MUIDrawer with bottom anchor, Paper.
Try itDrag the grips in the object navigation, command panel, and hero operation mobile examples.

Shared behaviors (both sheets)

  • The grip is the only drag handle: a 24px-tall touch target (touch-action: none) with a small rounded bar, pinned at the top of the sheet.
  • The sheet is position: fixed and overlays the canvas or preview — dragging it taller covers the content behind it; it never pushes layout around, and closing it never resizes the dock.
  • While the sheet is open, the content behind it re-centers in the remaining visible space: the selected object — or the bed when nothing is selected — fills the area above the sheet. The canvas applies a bottom inset equal to the sheet height (Canvas.tsx), and the hero preview gets paddingBottom equal to the sheet height (ImageCommandOverlay.tsx).
  • Release rules, evaluated in order: close if released in the bottom 10% of the viewport; snap to 50vh if released within 12vh of the midpoint; otherwise stay at the released height, clamped to 22–88vh.
  • Height transitions animate at 300ms ease-in-out when the sheet opens or closes.

Agent rules

  • Never render a bottom sheet on desktop; desktop uses the fixed side panel or the hero overlay's left controls column instead.
  • Never invent new drag thresholds, snap points, or close bands — any new mobile surface that needs a sheet must reuse these exact behaviors.
  • Pick the variant by anchor: panels that coexist with the dock use the command-panel numbers; full-screen operations use the hero numbers.

Inputs

Buttons and icon buttons

Buttons communicate actions. Icon buttons are for compact, repeated tools with familiar symbols and accessible labels.

MUIButton, LoadingButton, IconButton, ButtonGroup, Tooltip.
VariantsIn use: gf-button-primary (filled teal), gf-button-secondary (white with teal border), gf-button-danger (red). There are no tonal or text variants. A gf-button-premium (sunburst yellow) class exists in index.css but is not used anywhere — do not introduce it without a product decision.
States and variantsHover and focus enabled

Written context

  • Use one primary action per surface.
  • Use icon buttons for compact canvas tools with familiar symbols and accessible labels.

When to use which color

  • Primary (filled teal): the single main action of a surface — Print, Create, Add text, Apply. One per surface.
  • Secondary (white with teal border): every other non-destructive action — Preview, Cancel, alternatives next to a primary.
  • Danger (filled red): destructive actions only, such as removing an applied filter or deleting work. Always use a clear label (never icon-only) and confirm when the action is irreversible.
  • Do not introduce other button colors; the unused sunburst premium style stays out of the UI until a product decision says otherwise.

Code snippets

Desktop tokens:
panel padding 16px
doc section gap 24px
toolbar gap 4-8px
card radius 6px
button radius 999px
elevation: none — index.css forces all box-shadows
  (including arbitrary shadow-[...] classes) to none

Anatomy

  • Cards use 6px radius unless the surface is a hero overlay.
  • Buttons remain pilled.
  • The 2px cyan focus outline is mandatory.
  • The workspace renders flat: depth comes from borders and fills, never shadows. Do not add box-shadow utilities; the global suppression in src/index.css removes them.

Behaviors

  • Hover is subtle and color-only (no lift or shadow).
  • Active state uses cyan layer.
  • Disabled controls remain visible but muted.

Interactive example

  • The same tokens apply, but mobile surfaces use implemented dock and sheet chrome.

Code snippets

Mobile tokens:
bottom dock height 72px
draggable sheet radius 28px top corners
fixed action pill
hero controls as bottom sheet

Anatomy

  • Preserve 72px bottom dock.
  • Use draggable sheets rather than desktop side layouts.
  • Keep fixed action pill clear of dock and sheet.

Behaviors

  • Do not introduce desktop-only side layouts on mobile.
  • Keep active controls reachable when sheets are open.
